# Gate 3 Replay Outcome Evidence

This is the normative contract for the machine-readable evidence returned by an exact recovery replay. A replay result includes a `noesis.recovery-replay-evidence.v1` projection that binds the action ID and action digest to the committed completion receipt and to the verified persistent recovery-status snapshot.

| Field | Meaning |
|---|---|
| `status` | `passed` only after all bound evidence verifies. |
| `claim` | `true` only for a fully verified exact replay. |
| `action_id` / `action_digest` | Identity and canonical request binding for the replayed action. |
| `completion_receipt_id` | Reference to the immutable committed recovery completion receipt. |
| `status_snapshot_digest` | Digest of the verified status snapshot payload. |

`audit_replay_outcome()` is read-only. It never creates a receipt, repairs a snapshot, applies a rollback, or converts unavailable evidence into `not_run`. Missing, stale, corrupt, or mismatched evidence fails closed. Exact replay is idempotent only when this complete evidence set remains unchanged.

After a confirmed recovery completion, the executor atomically persists a signed `noesis.recovery-replay-evidence-snapshot.v1` sidecar. Exact replay must verify this sidecar against the current action, committed receipt, and status snapshot. Missing, tampered, or drifted replay snapshots are rejected before a `replayed` result is returned.

`audit_replay_snapshot_inventory()` is a deterministic, read-only projection with schema `noesis.recovery-replay-snapshot-inventory.v1`. It records the verified sidecar path, payload digest, action identity, action digest, and completion receipt identity. The signed replay snapshot carries the canonical sidecar path, and verification rejects a path mismatch before inventory projection. Duplicate JSON keys are rejected as conflicting records, while mismatched action identity or completion receipt identity raises an explicit identity-conflict error. Repeated audits over unchanged evidence must be byte-equivalent; verification failure is propagated fail-closed rather than producing a partial inventory.

After a confirmed replay snapshot is written, the executor atomically persists a signed `noesis.recovery-replay-snapshot-inventory-snapshot.v1` sidecar. Exact replay verifies this durable inventory snapshot against the current replay snapshot before returning `replayed`. Missing, corrupt, path-mismatched, tampered, or drifted inventory snapshots fail closed; no inventory snapshot is silently recreated during replay.

Replay and inventory sidecars are action-scoped and use a deterministic digest of `action_id` in their filenames. The recovery-status projection used by replay is also action-scoped, so two completed actions on one append-only event log cannot overwrite each other’s replay evidence or status evidence. Global operator status remains available as a separate aggregate snapshot.

`audit_replay_evidence_catalog()` is a read-only projection with schema `noesis.recovery-replay-evidence-catalog.v1`. It enumerates all action-scoped inventory sidecars, verifies their signatures and paths, binds each record to its replay snapshot, action event, committed completion receipt, and action-scoped status snapshot, and returns a deterministic catalog digest. Missing, duplicate, stale, path-conflicting, signature-invalid, or identity-conflicting records fail closed. Exact replay runs this catalog audit before returning `replayed`.

After catalog verification, the executor atomically persists a signed global `noesis.recovery-replay-evidence-catalog-snapshot.v1` sidecar. Exact replay verifies this durable aggregate snapshot against the current catalog. Missing, corrupt, path-mismatched, tampered, or drifted catalog snapshots block replay and are never silently recreated during replay.

The final write is a signed `noesis.recovery-replay-evidence-commit-manifest.v1` for each action. It binds the action, committed completion receipt, action-scoped status/replay/inventory snapshots, the global catalog snapshot, and a stable per-action completeness-record digest. The implementation may write a provisional manifest while a new action is being added, then refreshes the completeness snapshot and atomically rewrites the manifest as the final durable write. Exact replay verifies this final manifest last, so a partial evidence bundle cannot be promoted to `replayed`; missing, corrupt, path-mismatched, tampered, or drifted manifests fail closed without repair.

`audit_replay_evidence_completeness()` is a read-only startup-style audit with schema `noesis.recovery-replay-evidence-completeness.v1`. It requires one valid action-scoped commit manifest for every completed recovery event, validates receipt identity and manifest paths, and requires manifest count to equal both event count and catalog count. Any missing, duplicate, corrupt, conflicting, or uncommitted completion blocks the completeness claim. The audit independently recomputes each signed manifest `bundle_digest` before accepting count parity, so startup completeness cannot bypass whole-bundle tamper detection. It also requires every manifest-referenced event, status, replay, inventory, catalog, and completeness path to exist and match its canonical action-scoped path; only the completeness snapshot path may be absent during its first atomic bootstrap write. Existing signed sidecars are parsed with duplicate-key rejection and signature verification; corrupt or invalid sidecars fail closed before completeness is accepted. Action-scoped status, replay, and inventory payload identities and content digests are also compared with the corresponding manifest fields, preventing a validly signed but cross-action or stale sidecar from satisfying startup completeness. The durable global catalog snapshot is re-verified as well, and each manifest `catalog_record_digest` must match the immutable per-action catalog record before the completeness claim is accepted.

The completeness projection is also persisted as signed `noesis.recovery-replay-evidence-completeness-snapshot.v1`, including the deterministic `completeness_digest` over the ordered records and verified catalog digest. Before comparing the digest, verification requires the exact snapshot schema and `status=passed`, the canonical completeness path, non-negative integer event/manifest/catalog counts, a list of mapping records with unique action IDs, and a non-empty digest. The outer payload and every per-action record use fixed canonical field sets; unknown or missing fields are rejected rather than ignored. Duplicate JSON keys, malformed records, invalid count shapes, wrong status/schema, and count-shape conflicts fail closed with explicit reasons. The persistence path uses canonical sorted JSON and atomic replacement without timestamps or random fields. Rewriting unchanged completeness evidence must produce byte-identical snapshot bytes and the same signed payload; a fresh executor in the same or a separate Python process must reopen and verify the snapshot without regeneration. If the replacement step is interrupted, the previous canonical snapshot remains the only accepted evidence and must continue to verify unchanged; partial or orphan temporary files are never promoted, parsed, or used to silently repair a missing canonical snapshot. When a new completion event is appended before its completeness update finishes, the prior snapshot is intentionally stale and exact replay is blocked until an explicit final completeness write and final manifest write bind the complete multi-action catalog. The recovered two-action projection must be deterministic and include both manifests, records, and catalog entries. Corruption of any action-scoped manifest blocks the entire bundle with no partial `passed` claim, even when all other action evidence remains valid. The verifier never reconstructs a corrupted bundle from untrusted current state; explicit operator repair must restore a trusted signed manifest (or rebuild it from an independently trusted source), after which final completeness and manifest writes are required again and must be deterministic. The signed global catalog snapshot is an equally mandatory binding point: corruption, count drift, or record drift in that catalog blocks the whole multi-action bundle before count parity can be claimed. Trusted catalog restoration must be followed by deterministic catalog and completeness verification; no partial catalog count is accepted. Each action-scoped commit manifest must also bind the exact digest of its immutable catalog record. A validly signed catalog and validly signed manifest with a substituted record digest are still rejected at per-action binding, and restoration must return the original record digest before final verification can pass. Duplicate action IDs in completeness records and duplicate action IDs in the signed global catalog are rejected explicitly before count parity or digest acceptance. A clean trusted rebuild must remove the duplicate identity and then reproduce the same deterministic catalog and completeness bytes. Startup discovery is strict: every manifest filename in the event directory must correspond to exactly one expected completion action, and every expected action must map to a unique canonical manifest path. Unknown/orphan manifest files and canonical path-name collisions are rejected before any manifest is parsed or count parity is evaluated. The same strict allowlist applies to status, replay, inventory, catalog, completeness, and event sidecars: extra sidecar filenames are orphan evidence, and canonical sidecar paths must be regular files rather than symlink aliases. An alias or extra artifact therefore cannot satisfy a manifest binding through path normalization. Canonical evidence paths must resolve inside the event directory, and manifest/sidecar files must have single-link regular-file identity. Symlinks, hardlinks to an external target, and cross-bundle file aliases fail closed before payload acceptance; trusted repair must restore independent regular files inside the expected directory. Finalization is generation-bound even though each artifact is atomically replaced separately: an interrupted update that leaves a new signed sidecar beside an old manifest is rejected by the manifest-bound digest, while the unchanged old complete generation remains accepted. If the old generation is not intact, startup fails closed until an explicit rebuild writes and verifies every bundle member again. A signed `noesis.recovery-replay-generation-receipt.v1` now records the canonical event-sidecar and manifest file list, SHA-256 bytes for every regular file, and an immutable `generation_digest`. Startup verifies this receipt after the per-artifact checks; receipt drift, missing receipt, incomplete status, duplicate keys, or a changed file inventory blocks the generation as a whole. Rewriting an unchanged generation receipt is byte-identical, and trusted rebuild must regenerate the complete receipt only after all sidecars and manifests are final. Receipt payloads use an exact canonical field set; unknown or missing outer fields, unknown or missing file-record fields, duplicate JSON keys, stale schema versions, non-canonical paths, symlinks, hardlinks, duplicate file identities, invalid SHA-256 values, and out-of-directory paths fail closed. A fresh executor in a separate Python process must reopen and verify the same signed receipt without regeneration. Each receipt also carries a positive monotonic `generation_id` derived from the append-only completed-event count; the generation ID is included in the immutable digest projection. After a new completion event, the previous receipt is stale and cannot satisfy startup verification. Rotation from generation 1 to generation 2 is accepted only when the complete multi-action file inventory and final manifest set are present; skipped, regressed, or mismatched generation IDs fail closed. An interruption between receipt replacement and final manifest replacement therefore leaves either the previously complete generation or an explicitly rejected stale generation, never a mixed `passed` claim. The generation receipt also binds the current event-chain digest and completeness digest. Replacing those fields with values from an older event prefix, while retaining a valid signature, is rejected as generation drift; an old event prefix cannot be promoted as the current generation through receipt replay or rollback. Forked, duplicated, or reordered completion events are rejected by the append-only chain audit before generation digest comparison; generation verification therefore cannot hide a chain failure behind a receipt claim. Trusted repair must restore the original event order and unique action identities in the append-only source, after which the current generation receipt reopens and verifies deterministically. Startup-style replay auditing can require this durable snapshot explicitly; exact replay uses that mode and therefore cannot pass on a newly recomputed in-memory projection when the durable snapshot is missing. The signed snapshot is then verified against the current bundle and digest after the commit manifest gate. Missing, corrupt, path-mismatched, tampered, or drifted completeness snapshots fail closed and are never silently recreated during replay.

Before any replay evidence is promoted to `replayed`, the executor verifies the signed `noesis.recovery-event-chain-snapshot.v1` against the append-only completion event log. This check precedes action-scoped status verification so missing or drifted chain evidence reports the chain denial directly. The chain snapshot uses an exact canonical field set, exact schema version, non-negative count with event/receipt list parity, unique event identities, and a non-empty chain digest. Unknown or missing fields, invalid shape, stale schema, duplicate JSON keys, missing snapshot, and process-boundary drift fail closed. Rewriting an unchanged chain snapshot is deterministic, and a fresh Python process must reopen and verify it without regeneration; trusted rewrite is required before generation or replay acceptance resumes.

The action replay projection also audits the target action’s completion-event prefix and requires its final committed receipt ID to equal the replay record’s completion receipt ID. The resulting `event_chain_digest` is included in the signed replay evidence snapshot, preventing an action from being replayed against a different committed completion event. The final commit manifest carries the exact action-scoped `replay_event_chain_digest`; a validly signed manifest with an older-prefix substitution is rejected during manifest verification. Together, the signed event-chain snapshot, generation receipt, and final commit manifest form a cross-artifact chain binding: the generation receipt must match the current global chain, and each final manifest must match its current action-prefix chain before startup completeness can pass.

The final commit manifest additionally carries a deterministic `bundle_digest` over its canonical action-scoped fields. Verification recomputes this digest before accepting the manifest, binding the status, replay, inventory, catalog, completeness, receipt, and path projections as one evidence bundle.

Promotion is explicit and marker-last. `promote_replay_evidence_finalization()` first requires durable completeness and a passed generation receipt, then atomically writes a signed `noesis.recovery-replay-finalization.v1` marker containing the complete generation projection. Only after the marker exists does it remove owner/group/other write bits from every generation file, the generation receipt, and the finalization marker. Verification requires the marker, generation receipt, complete bundle, byte digests, regular-file identity, and read-only OS permissions. An interruption during the permission phase leaves a visible marker but fails closed as partial finalization; it can never be reported as finalized. Once the marker exists, every replay evidence writer rejects mutation with `recovery_replay_finalization_immutable`. A later file mutation or permission restoration is detected by generation digest drift or the finalization immutability check. Finalization is therefore an explicit promotion boundary, not an inferred status, and a fresh process must verify it without regeneration.

## Boundary

This proves local replay evidence binding and deterministic reporting. It does not prove process isolation, artifact restoration completeness, semantic safety, or native/external execution. Those claims require separate matching-host and pinned-revision evidence.
