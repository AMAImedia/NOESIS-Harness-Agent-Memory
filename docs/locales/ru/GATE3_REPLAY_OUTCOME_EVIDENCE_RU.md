# Gate 3 Replay Outcome Evidence — русская локализация

Это supplemental-описание English primary contract для machine-readable evidence, возвращаемого exact recovery replay. Replay result содержит projection `noesis.recovery-replay-evidence.v1`, связывающий action ID и action digest с committed completion receipt и verified persistent recovery-status snapshot.

| Поле | Значение |
|---|---|
| `status` | `passed` только после проверки всего bound evidence. |
| `claim` | `true` только для полностью проверенного exact replay. |
| `action_id` / `action_digest` | Identity и canonical request binding replayed action. |
| `completion_receipt_id` | Reference на immutable committed recovery completion receipt. |
| `status_snapshot_digest` | Digest verified status snapshot payload. |

`audit_replay_outcome()` является read-only. Он не создаёт receipt, не repair-ит snapshot, не применяет rollback и не превращает unavailable evidence в `not_run`. Missing, stale, corrupt или mismatched evidence fail-closed. Exact replay idempotent только пока весь evidence set не изменён.

После подтверждённого recovery completion executor атомарно сохраняет signed sidecar `noesis.recovery-replay-evidence-snapshot.v1`. Exact replay обязан проверить этот sidecar против current action, committed receipt и status snapshot. Missing, tampered или drifted replay snapshot отклоняется до возврата результата `replayed`.

`audit_replay_snapshot_inventory()` — deterministic read-only projection со schema `noesis.recovery-replay-snapshot-inventory.v1`. Он фиксирует verified sidecar path, payload digest, action identity, action digest и completion receipt identity. Signed replay snapshot содержит canonical sidecar path; path mismatch отклоняется до inventory projection. Duplicate JSON keys считаются conflicting records; mismatched action identity или completion receipt identity дают explicit identity-conflict error. Повторный audit неизменённого evidence обязан давать byte-equivalent результат; verification failure передаётся fail-closed без частичного inventory.

После подтверждённой записи replay snapshot executor атомарно сохраняет signed sidecar `noesis.recovery-replay-snapshot-inventory-snapshot.v1`. Exact replay проверяет durable inventory snapshot против current replay snapshot до возврата `replayed`. Missing, corrupt, path-mismatched, tampered или drifted inventory snapshot fail-closed; во время replay inventory snapshot не создаётся молча заново.

Replay и inventory sidecars являются action-scoped и используют deterministic digest `action_id` в filenames. Recovery-status projection, используемый replay, также action-scoped: две completed actions в одном append-only event log не могут перезаписать replay evidence или status evidence друг друга. Global operator status остаётся отдельным aggregate snapshot.

`audit_replay_evidence_catalog()` — read-only projection со schema `noesis.recovery-replay-evidence-catalog.v1`. Он перечисляет все action-scoped inventory sidecars, проверяет signatures и paths, связывает каждый record с replay snapshot, action event, committed completion receipt и action-scoped status snapshot, а также выпускает deterministic catalog digest. Missing, duplicate, stale, path-conflicting, signature-invalid или identity-conflicting records fail-closed. Exact replay запускает catalog audit до возврата `replayed`.

После проверки catalog executor атомарно сохраняет signed global sidecar `noesis.recovery-replay-evidence-catalog-snapshot.v1`. Exact replay проверяет durable aggregate snapshot против current catalog. Missing, corrupt, path-mismatched, tampered или drifted catalog snapshot блокирует replay и никогда не создаётся молча заново во время replay.

Последней записью является signed `noesis.recovery-replay-evidence-commit-manifest.v1` для каждой action. Он связывает action, committed completion receipt, action-scoped status/replay/inventory snapshots, global catalog snapshot и stable per-action completeness-record digest. При добавлении новой action implementation может сначала записать provisional manifest, затем обновить completeness snapshot и атомарно перезаписать manifest как final durable write. Exact replay проверяет этот final manifest последним: partial evidence bundle не может стать `replayed`; missing, corrupt, path-mismatched, tampered или drifted manifest fail-closed без repair.

`audit_replay_evidence_completeness()` — read-only startup-style audit со schema `noesis.recovery-replay-evidence-completeness.v1`. Он требует один valid action-scoped commit manifest на каждый completed recovery event, проверяет receipt identity и manifest paths, а также требует равенства manifest count, event count и catalog count. Missing, duplicate, corrupt, conflicting или uncommitted completion блокирует completeness claim. Audit независимо пересчитывает `bundle_digest` каждого signed manifest до принятия count parity, поэтому startup completeness не может обойти whole-bundle tamper detection. Он также требует существования и canonical path binding для event, status, replay, inventory, catalog и completeness paths каждого manifest; только completeness snapshot path может отсутствовать во время его первого atomic bootstrap write. Existing signed sidecars парсятся с duplicate-key rejection и signature verification; corrupt или invalid sidecar fail-closed до принятия completeness. Action-scoped status, replay и inventory payload identities и content digests также сравниваются с соответствующими manifest fields, поэтому validly signed cross-action или stale sidecar не может удовлетворить startup completeness. Durable global catalog snapshot также повторно проверяется, а каждый manifest `catalog_record_digest` должен совпадать с immutable per-action catalog record до принятия completeness claim.

Completeness projection также сохраняется как signed `noesis.recovery-replay-evidence-completeness-snapshot.v1`, включая deterministic `completeness_digest` по ordered records и verified catalog digest. До digest comparison verifier требует exact snapshot schema и `status=passed`, canonical completeness path, non-negative integer event/manifest/catalog counts, список mapping records с unique action IDs и non-empty digest. Outer payload и каждый per-action record используют fixed canonical field sets; unknown или missing fields не игнорируются и fail-closed отклоняются. Duplicate JSON keys, malformed records, invalid count shape, wrong status/schema и count-shape conflicts fail-closed с explicit reasons. Persistence path использует canonical sorted JSON и atomic replacement без timestamps и random fields. Повторная запись неизменённого completeness evidence должна давать byte-identical snapshot bytes и ту же signed payload; fresh executor в том же или отдельном Python process должен reopen и verify snapshot без regeneration. Если replacement прерван, предыдущий canonical snapshot остаётся единственным принимаемым evidence и должен продолжать проходить verification без изменений; partial или orphan temporary files не promoted, не parsed и не используются для silent repair missing canonical snapshot. Если новый completion event append-нут до завершения его completeness update, предыдущий snapshot намеренно stale, и exact replay блокируется до explicit final completeness write и final manifest write, связывающих полный multi-action catalog. Восстановленная двух-action projection должна быть deterministic и содержать оба manifest, record и catalog entry. Corruption любого action-scoped manifest блокирует весь bundle без partial `passed`, даже если evidence остальных action valid. Verifier никогда не реконструирует corrupted bundle из untrusted current state; explicit operator repair должен восстановить trusted signed manifest (или rebuild-ить его из independently trusted source), после чего final completeness и manifest writes должны быть выполнены снова и оставаться deterministic. Signed global catalog snapshot является equally mandatory binding point: corruption, count drift или record drift в catalog блокирует весь multi-action bundle до claim count parity. Trusted catalog restoration должна завершаться deterministic catalog и completeness verification; partial catalog count не принимается. Каждый action-scoped commit manifest также обязан связывать exact digest своего immutable catalog record. Validly signed catalog и validly signed manifest с substituted record digest всё равно отклоняются на per-action binding; restoration должна вернуть original record digest до успешной final verification. Duplicate action IDs в completeness records и duplicate action IDs в signed global catalog явно отклоняются до count parity или digest acceptance. Clean trusted rebuild должен удалить duplicate identity и воспроизвести те же deterministic catalog и completeness bytes. Startup discovery является strict: каждый manifest filename в event directory должен соответствовать ровно одной expected completion action, а каждая expected action должна иметь unique canonical manifest path. Unknown/orphan manifest files и canonical path-name collisions отклоняются до parsing любого manifest или оценки count parity. Та же strict allowlist применяется к status, replay, inventory, catalog, completeness и event sidecars: extra sidecar filenames являются orphan evidence, а canonical sidecar paths должны быть regular files, а не symlink aliases. Alias или extra artifact не может удовлетворить manifest binding через path normalization. Canonical evidence paths должны разрешаться внутри event directory, а manifest/sidecar files должны иметь single-link regular-file identity. Symlink, hardlink на external target и cross-bundle file alias fail-closed до payload acceptance; trusted repair должен восстановить независимые regular files внутри expected directory. Finalization generation-bound, хотя каждый artifact заменяется atomic отдельно: interrupted update, оставивший новый signed sidecar рядом со старым manifest, отклоняется по manifest-bound digest, тогда как неизменённая старая complete generation остаётся принимаемой. Если старая generation повреждена, startup fail-closed до explicit rebuild всех bundle members с последующей verification. Signed `noesis.recovery-replay-generation-receipt.v1` теперь записывает canonical event-sidecar и manifest file list, SHA-256 bytes каждого regular file и immutable `generation_digest`. Startup проверяет этот receipt после per-artifact checks; receipt drift, missing receipt, incomplete status, duplicate keys или изменённый file inventory блокируют generation целиком. Повторная запись неизменённого generation receipt byte-identical, а trusted rebuild должен регенерировать полный receipt только после finalization всех sidecars и manifests. Receipt payload использует exact canonical field set; unknown или missing outer fields, unknown или missing file-record fields, duplicate JSON keys, stale schema version, non-canonical paths, symlink, hardlink, duplicate file identity, invalid SHA-256 и path вне directory fail-closed. Fresh executor в отдельном Python process должен reopen и verify тот же signed receipt без regeneration. Каждый receipt также содержит положительный monotonic `generation_id`, полученный из append-only count completed events; generation ID входит в immutable digest projection. После нового completion event предыдущий receipt stale и не может удовлетворить startup verification. Rotation с generation 1 на generation 2 принимается только при наличии полного multi-action file inventory и final manifest set; skipped, regressed или mismatched generation ID fail-closed. Interrupted update между receipt replacement и final manifest replacement оставляет либо предыдущую complete generation, либо явно rejected stale generation, но никогда mixed `passed` claim. Generation receipt также связывает current event-chain digest и completeness digest. Подмена этих полей значениями старого event prefix при сохранении valid signature отклоняется как generation drift; старый event prefix не может стать current generation через receipt replay или rollback. Forked, duplicated или reordered completion events отклоняются append-only chain audit до generation digest comparison; generation verification не может скрыть chain failure за receipt claim. Trusted repair должен восстановить исходный event order и unique action identities в append-only source, после чего current generation receipt снова reopen и verify-ится deterministic. Startup-style replay audit может явно требовать этот durable snapshot; exact replay использует такой режим и поэтому не может пройти только на заново вычисленной in-memory projection при missing durable snapshot. Затем signed snapshot проверяется против current bundle и digest после commit manifest gate. Missing, corrupt, path-mismatched, tampered или drifted completeness snapshot fail-closed и никогда не создаётся молча заново во время replay.

До promotion любого replay evidence в `replayed` executor проверяет signed `noesis.recovery-event-chain-snapshot.v1` против append-only completion event log. Эта проверка выполняется до action-scoped status verification, поэтому missing или drifted chain evidence сообщает direct chain denial. Chain snapshot использует exact canonical field set, exact schema version, non-negative count с parity event/receipt lists, unique event identities и non-empty chain digest. Unknown или missing fields, invalid shape, stale schema, duplicate JSON keys, missing snapshot и process-boundary drift fail-closed. Повторная запись unchanged chain snapshot deterministic, а fresh Python process должен reopen и verify его без regeneration; trusted rewrite обязателен до возобновления generation или replay acceptance.

Action replay projection также проверяет completion-event prefix target action и требует, чтобы его final committed receipt ID совпадал с completion receipt ID replay record. Полученный `event_chain_digest` входит в signed replay evidence snapshot и не позволяет replay against different committed completion event. Final commit manifest содержит exact action-scoped `replay_event_chain_digest`; validly signed manifest со старым-prefix substitution отклоняется при manifest verification. Signed event-chain snapshot, generation receipt и final commit manifest вместе образуют cross-artifact chain binding: generation receipt должен совпадать с current global chain, а каждый final manifest — с current action-prefix chain до startup completeness pass.

Final commit manifest дополнительно содержит deterministic `bundle_digest` по canonical action-scoped fields. Verification пересчитывает digest до принятия manifest и связывает status, replay, inventory, catalog, completeness, receipt и path projections как единый evidence bundle.

Promotion является explicit и marker-last. `promote_replay_evidence_finalization()` сначала требует durable completeness и passed generation receipt, затем atomic записывает signed marker `noesis.recovery-replay-finalization.v1` с полной generation projection. Только после появления marker снимаются owner/group/other write bits со всех generation files, generation receipt и finalization marker. Verification требует marker, generation receipt, полный bundle, byte digests, regular-file identity и read-only OS permissions. Interrupted permission phase оставляет видимый marker, но fail-closed как partial finalization; он никогда не считается finalized. После появления marker каждый replay evidence writer отклоняет mutation с `recovery_replay_finalization_immutable`. Последующая подмена файла или восстановление write permissions обнаруживаются как generation digest drift либо finalization immutability failure. Finalization является explicit promotion boundary, а не выведенным статусом; fresh process должен проверить её без regeneration.

`verify_replay_evidence_readiness(require_finalized=True)` является startup-style strict gate. Он требует durable completeness snapshot, generation receipt и valid immutable finalization marker; missing marker возвращает `recovery_replay_finalization_required`, а marker с interrupted permission phase fail-closed как `recovery_replay_finalization_not_immutable`. Executor может включить эту политику через `require_finalized_replay=True`; тогда exact replay не может вернуть `replayed`, пока generation не будет explicit promoted и verified. Default сохраняет compatibility для provisional local evidence, но strict production/readiness lanes обязаны включать finalized requirement.

Partial finalization marker нельзя overwrite-ить или молча удалять. `repair_replay_evidence_finalization()` сначала проверяет, что failure marker ограничен immutability, повторно проверяет durable completeness и generation receipt, архивирует partial marker в `_archive/`, восстанавливает write permission только для trusted generation files и запускает тот же marker-last promotion path. Signature, schema, path, generation или digest corruption не repair-ится этим методом и остаётся для operator investigation. Valid finalized marker также не repair-ится; повторный repair возвращает `recovery_replay_finalization_already_finalized`. Re-finalization deterministic: новый active marker и все generation bytes должны идентично пройти verification против trusted generation projection, а прежний partial marker сохраняется как archived evidence. Успешный repair дополнительно записывает signed receipt `noesis.recovery-replay-finalization-repair.v1`. Этот receipt связывает current generation ID и digest, archived partial-marker path и SHA-256, active finalization path и SHA-256, а также собственный repair digest. Verification требует, чтобы archived file оставался независимым regular file внутри bundle `_archive/` с ожидаемым finalization basename; valid signature не может разрешить foreign-bundle archive substitution. Finalization verification автоматически проверяет этот repair receipt, если он существует, поэтому stale, substituted или modified repair provenance блокирует readiness. Repair receipts также образуют append-only signed JSONL chain по canonical repair-chain path. Каждый receipt содержит положительный monotonic `repair_id`, previous repair digest, `repair_event_digest` и chain path; verification отклоняет missing links, duplicate IDs, reordered records, digest forks или current receipt, не являющийся chain tip. Следующий repair архивирует prior active receipt перед append следующей записи, сохраняя полную repair history. Сам repair chain становится read-only после append и входит в strict sidecar discovery, поэтому orphan или substituted chain file не может быть проигнорирован startup completeness. Chain append flush-ит полный signed JSONL record и вызывает `fsync()` до повторной защиты chain. Crash, оставивший truncated или malformed terminal record, не считается recoverable success: verification fail-closed как `recovery_repair_chain_partial_record`, а symlink или hardlink identity change — как `recovery_repair_chain_file_identity`. Active repair receipt поэтому не может разрешить finalization, пока весь append-only chain не остаётся parseable, ordered, independently linked и physically single-linked.

Repair-chain readiness audit публикует отдельный snapshot `noesis.recovery-repair-chain-readiness.v1`. Его state равен `missing`, если repair ещё не происходил; `passed`, если весь immutable chain valid; `partial` для writable или truncated chain; `reordered` для monotonic-link violations; `corrupt` для malformed records или file-identity violations; `immutable` только для valid non-empty chain, у которого protection state известен, но active receipt ещё не принят. Audit намеренно non-throwing для operator observability, тогда как `verify_replay_evidence_readiness()` остаётся fail-closed и поднимает underlying recovery error, если finalized generation зависит от invalid chain. Diagnostic snapshot не может стать acceptance bypass. После успешного repair audit сохраняется как signed receipt `noesis.recovery-repair-chain-readiness.v1`. Его payload связывает chain tip digest, ordered repair IDs, immutable chain path, current status и active finalization SHA-256 через `readiness_digest`. Он также содержит `generation_id`, `generation_digest`, `event_chain_digest`, `completeness_digest` и `chain_root_digest`; последний обязан совпадать с event-chain root в generation receipt. Verification требует receipt signature, exact current chain projection, current generation receipt, exact finalization bytes и read-only permissions. Stale или validly re-signed receipt для другого chain tip, generation, completeness projection или event-chain root отклоняется как readiness drift и не принимается как operator telemetry. Fresh executor process может проверить тот же bound snapshot без regeneration evidence. Repaired finalized bundle также получает signed inventory `noesis.recovery-replay-finalized-inventory.v1`. Inventory содержит canonical event-chain file, generation receipt, finalization marker, repair receipt, append-only repair chain и signed readiness snapshot — каждый с SHA-256 — вместе с generation IDs, completeness digest, event-chain root, repair-chain tip и `inventory_digest`. Inventory read-only и принимается только если каждый listed file остаётся regular single-link file по canonical path с теми же bytes, а strict sidecar discovery не находит unlisted sibling. Validly re-signed inventory не может разрешить foreign artifact set: generation drift, chain-root drift, repair-tip drift, orphan sidecars или file substitution fail-closed. Finalized bundle также создаёт signed receipt `noesis.recovery-replay-inventory-verification.v1`. Он связывает verification result с inventory digest, generation digest, chain root, readiness status, finalization status и canonical verification path через `verification_digest`. Strict startup readiness проверяет этот receipt, если он существует; stale, replayed, modified или validly re-signed receipt для другой inventory fail-closed и не принимается как эквивалентный verification outcome. Каждый успешный verification receipt также append-ит signed record в canonical JSONL chain `noesis.recovery-replay-inventory-verification-run.v1`. Run IDs положительные и monotonic; каждая запись связывает current inventory digest, verification digest, receipt signature, previous run digest и собственные event/run digests. Chain flush-ится и получает `fsync()` до read-only protection. Startup verification отклоняет missing links, reordered records, duplicate IDs, signature/digest forks, foreign inventory substitution, writable или aliased chain. Повторная verification создаёт следующий audit run, а не перезаписывает history. Отдельный audit `noesis.recovery-replay-inventory-verification-chain-readiness.v1` публикует `missing` до первого run, `passed` для valid immutable chain, `partial` для writable или incomplete chain, `reordered` для monotonic-link violations и `corrupt` для identity, signature, digest или current-receipt drift. Audit diagnostic-only; strict fresh-process startup поднимает underlying failure и никогда не превращает `partial`, `reordered` или `corrupt` в acceptance. Новый executor сообщает `passed` только после повторной проверки current inventory-verification receipt и полного chain. Успешный finalized bundle также сохраняет signed snapshot `noesis.recovery-replay-inventory-verification-chain-readiness.v1`. Snapshot связывает run-chain tip digest, run count, inventory digest, verification digest, canonical chain/inventory paths и явные `readiness_result` и `verification_result` через `readiness_digest`; затем становится read-only и входит в strict sidecar discovery. Verification заново вычисляет current chain, inventory и receipt перед сравнением signed snapshot. Stale, modified или validly re-signed snapshot для другого run tip или inventory fail-closed как `recovery_inventory_verification_readiness_drift`, включая fresh executor process.
