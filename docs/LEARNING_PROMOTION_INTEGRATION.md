# Learning Promotion Integration Contract

This contract connects terminal task outcomes from the durable task/session event stream to the human-governed learning promotion pipeline without enabling automatic skill activation.

## Integration surfaces

| Surface | Contract |
|---|---|
| Durable event stream | `PromotionEventBridge` replays append-only `task_state_changed` events. Only `committed` and `failed` states are eligible for capture; `cancelled` is explicitly denied. |
| Terminal mapping | `committed` becomes a successful promotion outcome; `failed` becomes a failure outcome. Active, review, planned and unknown states are ignored by the bridge. |
| Policy simulation | `OwnershipPolicySimulator` derives the decision from authoritative task/session metadata and an explicit runtime owner lookup; it delegates deterministic digest construction to `RuntimePolicySimulator`. It performs no side effects. Session mismatch, missing owner, denied scope, malformed metadata and lookup errors fail closed. |
| Durable checkpoints | The bridge writes `started`, `completed` and `denied` checkpoint events keyed by source task event ID. Completed and denied events are not replayed. Existing receipts are reused by experience ID to absorb safe retries. |
| Evaluator registry | Evaluator versions must be registered explicitly and uniquely. Unknown or duplicate versions fail closed. Evaluators provide deterministic holdout cases; they do not promote anything. Durable manifests are evidence of registration intent, not runtime availability: after restart, a persisted version without a re-registered callable is `blocked`, and manifest conflicts fail closed. `noesis.evaluator-readiness.v1` exposes registered/persisted versions, missing runtime versions and conflicts. |
| Promotion operations | Capture, evaluate, propose, approve, promote and rollback are explicit method calls. `TaskExecutionBridge.poll_promotion_events(operator_trigger=True)` is the only lifecycle entry point for bridge polling; `execute()` never polls or promotes implicitly. |
| Operator administration | `AdministrativePolicyStore` is a reviewed, session-bound source for reviewer grant/revoke operations. It requires an active administrator session and `admin:reviewers` scope. Each accepted mutation carries a HMAC-signed `noesis.signed-mutation-receipt.v1` audit receipt; duplicate state transitions fail as conflicts. Optional `CoordinatedMutationJournal` records `prepared`, `committed` or `aborted` mutation phases. An uncommitted prepared action is reported as `incomplete` and is never auto-promoted or silently reconciled. `OperatorSessionActionExecutor` applies explicit, idempotent open/close actions with the same signed receipt contract; optional `POST /api/operator-sessions` and `POST /api/admin/reviewer-policy` only validate and delegate to injected handlers.
 |
| Operator approval UI | `PromotionApprovalAction` is a versioned non-secret action envelope for `approve`, `reject` and `rollback`. `OperatorSessionRegistry` persists operator sessions with scopes and bounded TTL, and derives active `OperatorAuthContext` values. `ReviewerAuthorizationStore` persists reviewer grants and revocations; absent, revoked, expired or scope-mismatched authorization fails closed. `PromotionActionExecutor` applies only explicit proposal operations, requires an independent authorized reviewer, signs a receipt and stores an idempotent action record. Optional authenticated `POST /api/promotion-actions` validates the envelope and passes both action and configured operator context to an injected handler; the HealthServer never performs promotion itself. |
| Operator telemetry | Lifecycle and denial events are bounded, redacted and exposed under the optional `learning_promotion` section of the read-only HealthServer telemetry snapshot and existing SSE snapshot. The snapshot includes evaluator readiness without evaluator callables or content. |
| Activation | Integration defaults `activate=False`; active skill pointers cannot be created by task completion, policy simulation, UI action validation, approval action execution or evaluation. |
| Production lifecycle facade | `ProductionLearningLifecycle` composes the durable task store, `PromotionEventBridge`, an injected runtime-owned policy simulator and `PromotionActionExecutor`. `capture_terminal_events()` requires `operator_trigger=True`; `handle_operator_action()` remains a separate authenticated operation. Its readiness contract reports automatic evaluation, approval, promotion and activation as disabled. |
| Durable promotion state | `LearningPromotionPipeline` stores receipts, evaluations, proposals, previous-active metadata and evaluator manifests in SQLite/WAL. A reopened pipeline reconstructs bounded state; malformed or conflicting evaluator manifests fail closed. |
| Retry and conflict boundary | Repeating an identical capture, holdout evaluation or proposal returns the existing record. Reusing an identity with a different payload, holdout manifest or proposal content raises an explicit conflict instead of silently overwriting state. |

## Event boundary

The integration emits `experience_captured`, `holdout_evaluated`, `promotion_proposed`, `promotion_approved`, `promotion_completed`, `promotion_rolled_back` and `promotion_blocked`. Telemetry contains identifiers, states, counts, digests and bounded denial reasons only. Content-like fields, credentials and API keys are recursively redacted.

## Recovery and retry semantics

The bridge is replay-safe for a repeated poll and a newly constructed bridge using the same checkpoint path. A source event with a completed or denied checkpoint is skipped. A started checkpoint without a terminal checkpoint may be retried; receipt lookup by experience ID prevents duplicate capture after a crash between capture and checkpoint append. EventStore repairs only a malformed final JSONL tail; non-tail corruption remains a hard failure.

Operator actions are separately replay-safe by `action_id`. A completed action returns its stored signed receipt instead of reapplying the state transition. `verify_signed_mutation_receipt` detects tampering or wrong signing keys. The optional `CoordinatedMutationJournal` uses prepare/apply/commit coordination; `incomplete()` exposes prepared actions lacking a terminal record, while `abort` makes an interrupted operation explicit. This is coordination, not a claim of cross-file atomicity. Identity, session and optional scope mismatches fail closed and emit bounded `promotion_action_denied` telemetry; replay emits `promotion_action_replayed`. `OperatorSessionRegistry` reconstructs sessions from append-only events and denies inactive, closed or expired sessions. Administrative reviewer grants require an active administrator session with `admin:reviewers`; unauthorized grant/revoke attempts are rejected before policy mutation, and repeated grant/revoke states fail as conflicts. If a mutation log has a malformed final tail, EventStore truncates only that tail and replay remains fail-closed for incomplete actions; non-tail corruption is not repaired. Reviewer authorization is append-only and persistent: a grant must match operator/session and required scope, while missing or revoked grants deny. Approval requires an independent authorized reviewer relative to the experience owner. `reject` is allowed only from `review`; `rollback` is allowed only from `promoted` and does not activate anything. Promotion approval and activation remain outside task-event replay and are never inferred from a checkpoint.

## Non-goals

This layer does not execute skill content, choose an evaluator implicitly, activate a skill automatically, or claim general autonomous learning. It is a governed bridge to the existing promotion state machine. `SQLiteAdministrativeBackend` provides an optional single-store SQLite/WAL backend in which operator sessions, reviewer grants and signed mutation audit rows commit in one database transaction. A failed transaction leaves neither the state mutation nor its audit row. `AdministrativeMigrationAdapter` records versioned `legacy`, `dual_read` and `sqlite` modes, blocks direct legacy-to-sqlite cutover, compares authoritative identity/scopes/active state before adoption, and exposes explicit rollback to `legacy`. `AdministrativeActionRouter` selects the legacy handler by default, blocks `dual_read`/`sqlite` routing on a failed verification, and selects the SQLite handler only after an explicit verified mode transition. Its `health_handler()` is compatible with the injected HealthServer mutation handler contract and emits a bounded routing evidence event. Its `promotion_handler()` parses the versioned `PromotionApprovalAction` envelope and delegates to the selected real executor's `handle()` method; it does not bypass reviewer/session authorization. TTL timestamps are intentionally compared by semantic state rather than byte equality. Automatic cutover remains disabled. `OperatorMigrationModeSource` is an append-only, operator-owned mode source whose safe default is `legacy`; direct `legacy` to `sqlite` is rejected. HealthServer accepts the source at startup, exposes `/api/readiness`, and includes `migration_readiness` in telemetry and health evidence. The readiness snapshot reports `legacy`, `dual_read`, `sqlite`, `blocked`, and `rollback_available`; a blocked migration maps to the UI contract's allowed `unavailable` health status while retaining `blocked` in the machine-readable snapshot. The authenticated POST `/api/admin/migration-mode` accepts the versioned `noesis.migration-mode-action.v1` envelope, delegates only through an injected operator context, and returns an HMAC-signed mode-change receipt. The self-contained Cloudflare-style control-plane UI renders the readiness card, rollback state and mode-change controls, while the telemetry SSE stream updates the same panel. Runtime activation remains a separate capability-gated implementation task. The production facade is a binding and policy boundary, not an autonomous learning loop: it does not evaluate, approve, promote or activate as a side effect of task completion. `PromotionIntegration.snapshot()` exposes only bounded counts, evaluator manifest digests and `noesis.evaluator-readiness.v1`; payload, evaluator callables and skill content remain outside operator telemetry.

Gate 2 tests cover restart reconstruction, evaluator manifest conflict, duplicate idempotency and bounded state.

## 2026-08-21 — External identity-provider preparation

`ExternalIdentityPreparation` is the bounded local preparation surface for `LEARN-ADMIN-06`. It accepts already-decoded claims and validates a trusted issuer allow-list, exact configured audience membership, non-empty subject, bounded expiry, and required administrative scopes. It produces a stable `PreparedExternalIdentity` with a canonical claims digest and can derive an authenticated `OperatorAuthContext` only for an explicitly supplied local session ID. No provider SDK, network call, token signature verification, key discovery, login, or refresh is performed. `readiness()` therefore reports `prepared_not_run` and `external_verification: NOT_RUN`; a pinned provider adapter remains required before external identity behavior can be claimed.

Implementation: `noesis_harness/external_identity.py`; focused tests: `tests/test_external_identity.py`. The preparation contract is provider-neutral and fail-closed; it is not an external identity-provider integration.
